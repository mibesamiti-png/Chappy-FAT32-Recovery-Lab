## Safety and evaluation contract

- Work with generated data only. The physical microSD, sole 31 GB master and actual files are excluded from reading, hashing, copying, writing, repair, experiments and upload. The [real-image gate](LOCAL_READONLY_APPROVAL_GATE.md) remains **NOT APPROVED**. No physical-device handles, CHKDSK or format operations.
- Analysis consumes readable, seekable, non-writable streams. Separate source handles, manifest/ground-truth storage and candidate output. Never feed source hashes, correct extents, lengths or positions to discovery unless the trial explicitly evaluates a documented hint. Record any hints, including alignment and search window.
- Record seed, generator revision, fixture ID, input SHA before/after, method revision and flags. Hash full generated originals and exact reconstructed bytes independently. Score TP/FP/FN/TN with the unit and denominator defined before each experiment. Report exact matches, false original claims, ambiguity and unknown separately. Record requested and actual reads, unique regions, candidates/probes, elapsed time and memory high-water where measurable.
- Set explicit per-run bounds before measuring. Stop with coded partial/unknown status on exhausted budgets, short reads or unresolved evidence. Block integration for input mutation, path escape, privacy leak, unsupported licensing, uncontrolled work, false original verification or failed required CI. Record the failing case and leave the issue open when safe resolution is unavailable.
- Publish source, invented data generators and sanitized metrics. Keep generated images, private paths, actual names, recovered files and unredacted logs out of GitHub. Verify exact licenses and attribution before reuse. Treat GPL or mixed-license code as unavailable for copying until license review is complete.

## Review, dispatch and progress

Use small Draft PRs, freeze the relevant baseline and score before promotion. A reviews and merges accepted changes. Keep production-facing new inference default off while experimental. Preserve active B #60, C #61 and D #62 branches and ownership. For each follow-up, A records the current disposition, pins a reviewed fixture revision, creates a new Issue and dedicated branch from current main, and updates the live roster. Do this independently for each team to avoid duplicate work.

Track four statuses per stage: implementation, test, integration and documentation. Use pending, in progress, passed or blocked and link the evidence. The weighted completion percentage is the sum of the weights of stages whose full gates pass. Report partial work in the four statuses and report B/C/D against their own stage gates. On merging this plan, the first checkpoint is 5% (R0); other stages get credit only after their listed gates. The percentage tracks artificial-system engineering milestones.

For every round record the date, current main, issue and branch, changed PR and head, tests run and failures, CI links, current four statuses and weighted total, safety/known issues, and the next bounded operation. The issue and PR record active changes. STATE summarizes accepted milestones.
