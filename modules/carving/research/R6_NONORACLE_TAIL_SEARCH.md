## R1: immutable artificial A/B corpus and baseline

- Entire source: deterministic 128KiB, 512B-cluster FAT32-*like* artificial byte buffer inherited from R4/R5 tests; **not a mountable FAT32 volume**. No downloaded data.
- Original invented G-code first offset 20,480 and tail offset 40,960, 512B first slice; 3MF first 61,440 and tail 90,112, 512B first slice. Each tail size (<=512B) is known to the synthetic test. **Neither correct tail offset is given to R6 as an input or prefiltered list.**
- Five scenarios: one G-code true tail; G-code plus syntax-valid altered tail; one 3MF true tail; 3MF plus modified central-directory metadata tail (still structurally valid but byte-different); true 3MF tail outside an explicitly bounded 64KiB scan. All use the same generated bytes for baseline and candidate within each scenario.
- Baseline: production `Get-ChappyCarvingCandidates` contiguous scanner, with `MaxScanBytes` equal to the scenario's 64/128KiB window, `ExtraValidationReadBytes=4096`, max 256 probes and 30s time. Baseline produces no complete artificially original-byte-identical join on any of these physically split cases.
- Candidate: `Test-R6NonOracleSyntheticTailSearch` is **ONLY** in the C test file `R6NonOracleResearch.ps1`; 512B grid scans a full 128KiB (or explicit 64KiB) range without tail hints. A cheap ASCII G/M/T command-line prefix or ZIP EOCD marker promotes at most 8 grid positions to the existing R5 two-fragment in-memory format validator. The validator itself may yield ambiguous positives and is not a proof of original data.
- Both paths have a **same ceiling** of 135168B actual source stream reads and 30s per test, with read-only in-memory Streams. Candidate additionally has at most 256 grid probes, 8 candidate pairs, 512B per fragment, 73728B in-memory validator read ceiling. Existing baseline's probes count format anchors, whereas candidate grid probes count sampled blocks; those metrics are NOT equivalent.
- **Important remaining metadata privilege:** R6 still receives a known first offset, exact first size and artificial true second-length size; it assumes 512B alignment and a constrained 128KiB search region. These are **not** discovered from a real damaged FAT32 device. This study does not estimate generic search success or speed.

## R2: algorithm and safety

- Search is bounded to the declared artificial window, aligned 512B steps. Read only the specified short tail-length at each offset with strict accounting, including short reads.
- No buffer larger than a single <=512B tail plus the existing <=1024B in-memory candidate; default-disabled DEFLATE remains OFF. No FAT chain follow, no user path, output file, disk repair, extraction, network, admin privilege or physical device.
- Stop with `status=partial`, `decision=incomplete` on time/read/grid/pair overrun. Never silently drop excess candidates and call one original. Return `one_possible`, `ambiguous` or `unknown`, not actual recovered/verified-original.
- Additional failures under test: writable stream refused; >8 plausible decoy tails; max 4 grid probes; 1024B source cap. Source SHA must remain byte-identical.

## R3: observed controlled synthetic results (initial CI)

Actual Windows PowerShell 5.1 [CI #43038830398](https://github.com/mibesamiti-png/Chappy-FAT32-Recovery-Lab/actions/runs/43038830398) (implementation HEAD `203371a477ca8bd4b2387bd133d66e12f20debdb`) passed. It measured:

| Measure | Contiguous-only baseline | R6 unhinted-grid experimental candidate |
|---|---:|---:|
| Complete matches to independently known invented original bytes | 0 of 5 scenarios | 4 accepted correct pairs (of 6 format-accepted pairs) |
| Incorrect but format-consistent synthetic pairs | Not enumerated | 2 (one G-code; one modified 3MF metadata) |
| Cases with unambiguous single candidate | 0 | 2 of 5 |
| Cases with multiple format-consistent candidates | Not applicable | 2 of 5 |
| Correct tail outside scan coverage | Not recovered | 1 of 5, returned unknown |
| Sampled 512B grid offsets | Not applicable (signature scanner) | 1,147 across 5 cases |
| Pair trials given to format validator | Not applicable | 6 |
| True-positive / false-positive accepted pairs | Not directly comparable | 4 / 2 |
| False-negative unavailable true tail | 5 scenarios lack complete contiguous original | 1 (outside 64KiB scenario window) |
| Rejected sampled offsets (TN opportunities) | Not directly comparable | 1,141 |
| Total actual source bytes read across five cases | 458,872 B | 195,343 B |
| Total separate in-memory validator reads | Included in baseline's source read metric | 9,366 B |
| False claim of intact original bytes | 0 | 0 (candidate code never claims original) |

Pair-level precision on these six accepted artificial pairs is **4/6**; defined positive opportunity recall across five known original files is **4/5**. These aggregate different granularities and must **not** be treated as a general device recovery probability or paired A/B precision delta. Most negative grid offsets are trivially zero by construction. A stronger benchmark must include real-like nonzero noisy clusters, different alignments, unknown tail lengths and candidate pair orderings.

Follow-up adversarial flood/byte-cap tests were appended after that initial CI; **final exact-HEAD CI evidence is required before integration**. Timing is platform/jitter-dependent, and the candidate's known first position/second length prevents a fully fair generic performance comparison.
